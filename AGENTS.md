# Project Overview

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

## Agent roles

Two primary agent types are distinguished in this repository's design, and one additional review-only agent role is defined for repository assessment. Documentation and docstrings MUST use these terms when referring to one of them; see [DR-003](docs/dev/decision-records/DR-003%20Research%20Agent%20and%20Development%20Agent%20Terminology.md).

- **Research Agent**: Deployed or runtime agent; subject of research. Sees tools, system prompts, and generated schema (e.g. from middleware/MCP); does NOT see repository, design docs, or AGENTS.md. Framework names such as LangGraph `AgentState` and "DeepAgents" refer to this side.
- **Development Agent**: Code agent (e.g. Cursor, Claude Code). Reads AGENTS.md and design docs; modifies code and documentation; develops code for the Research Agent and documentation for itself. MUST be aware of the distinction between the two types.
- **Critique Agent**: Repository-wide review agent used for technical due diligence, portfolio review, or holistic critique. It MAY inspect any repository content when that inspection is relevant to the review, including content that local `AGENTS.md` files ask Development Agents to ignore. It MUST treat such material as review evidence rather than authoritative implementation guidance.

Most agents interacting with this repository are Development Agents. An agent MUST NOT assume that it is a Critique Agent unless the user, governing prompt, or invoked skill explicitly assigns that role.
Local `AGENTS.md` files SHOULD assume a Development Agent audience unless they explicitly address another role. A local `AGENTS.md` MUST NOT be interpreted to narrow the repository-wide inspection scope of an explicitly designated Critique Agent.

---

This repository MUST support research into agents and their interoperability
with formal logic. It SHOULD support the wider research community studying
agents as the monorepo for the `rdflib-reasoning` Python libraries:

- Development MUST use the `rdflib-reasoning` conda environment.
- All use [src-layout](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)
- All use the `rdflib_reasoning` [namespace package](https://packaging.python.org/en/latest/guides/packaging-namespace-packages/) with a shared **PEP 420** implicit namespace at the `rdflib_reasoning` root (no root `__init__.py` in published wheels; subpackages merge at runtime across distributions)

Repository map:

- `docs/`: Reference materials for humans and machines.
- `docs/dev/`: Authoritative architecture, roadmap, decision records, and
  development status.
- `docs/dev/decision-records/`: Rationale and history for architecture and
  planning.
- `docs/specs/`: Cached specifications optimized for Development Agent and
  tooling use.
- `notebooks/`: Research, demonstration, tutorial, and evaluation notebooks.
- `rdflib-reasoning-middleware/`: Research Agent-facing middleware and
  capability gating; see its `AGENTS.md` and
  [README](rdflib-reasoning-middleware/README.md).
- `rdflib-reasoning-axioms/`: Structural RDF/OWL models and graph-backed schema
  contracts; see its `AGENTS.md` for local modeling and schema rules.
- `rdflib-reasoning-engine/`: RDFLib-integrated RETE-based RDFS and OWL 2 RL
  entailment, proof, and contradiction diagnostics; see its `AGENTS.md` for
  engine-specific rules.
- `script-helpers.sh`: Bash helper functions for repository scripts.

## Docstring standard and public API documentation

Python docstrings in this repository MUST use
[Google-style docstrings](https://www.sphinx-doc.org/en/master/usage/extensions/napoleon.html)
as parsed by Sphinx Napoleon. NumPy-style docstrings MUST NOT be introduced.

Docstrings are part of the published package documentation generated by Sphinx
AutoAPI. Public module, class, function, method, attribute, and dataclass or
Pydantic model docstrings MUST be written for package consumers and downstream
Python developers first. They MUST describe current behavior only; planned
behavior belongs in [docs/dev/roadmap.md](docs/dev/roadmap.md),
[docs/dev/architecture.md](docs/dev/architecture.md), or decision records.

Public docstrings MUST:

- Start with a concise summary sentence.
- Use Google-style sections such as `Args:`, `Returns:`, `Yields:`, `Raises:`,
  `Attributes:`, `Examples:`, and `Note:` only when they add useful information.
- Treat Python type annotations as the primary source of parameter and return
  types; prose SHOULD explain semantics, constraints, side effects, mutation,
  RDF term forms, graph-context behavior, and error conditions rather than
  restating obvious types.
- Use "Research Agent" and "Development Agent" exactly as defined in this file
  when referring to one of those roles.
- Prefer official specification names, stable public URIs, package public API
  names, and compact lexical examples over repository-local references.
- Avoid repository-local specs, crosswalks, `AGENTS.md` files, design docs,
  source comments, or unpublished planning artifacts.

Public docstrings SHOULD exist for every exported or documented public object.
Private helpers MAY omit docstrings when their behavior is local and obvious,
but SHOULD have docstrings when they encode non-trivial invariants, algorithms,
or boundary behavior.

Docstring drift is a correctness issue. When changing public behavior, public
parameters, return values, exceptions, side effects, schema-visible behavior,
tool-visible behavior, supported RDF forms, or implementation details described
by an existing public docstring, the Development Agent MUST update the relevant
docstrings in the same change. A change MUST NOT leave a docstring describing
old behavior, planned behavior, removed arguments, obsolete exceptions, or
unsupported RDF forms.

When adding a new public module, class, function, method, dataclass, Pydantic
model, or exported notebook helper, the Development Agent SHOULD add the public
docstring in the same change. If the new public object intentionally ships
without a docstring while the repository is still backfilling missing
docstrings, the Development Agent MUST ensure no misleading nearby docstring
appears to document it and SHOULD keep the omission local to the narrowest
reasonable scope.

When moving, renaming, splitting, merging, or deleting public objects, the
Development Agent MUST review the moved object's docstrings, module docstrings,
package `__init__.py` docstrings, and any affected AutoAPI/Sphinx references so
published API documentation continues to match the import surface.

Docstring edits MUST be validated with `make check`. Before enabling any of
`D100` through `D107` for a wider scope, the Development Agent SHOULD run a
targeted Ruff check such as
`uv run ruff check . --select D100,D101,D102,D103,D104,D105,D106,D107` and
confirm that remaining violations are intentional backfill work rather than
tests, generated files, notebook cells, or other excluded surfaces.

Package-local `AGENTS.md` files MAY add stricter docstring requirements for
their local domain, but they MUST remain consistent with this repository-wide
standard.

## Sphinx documentation policy

Published package documentation is authored under `docs-src/` and built with
Sphinx. It is package-consumer documentation first: it SHOULD help downstream
Python developers install, understand, extend, and correctly use the
`rdflib-reasoning` packages. Research context MAY appear when it clarifies
motivation or examples, but it MUST NOT make the project look like notebooks
first and reusable Python packages second.

Sphinx pages MUST NOT duplicate generated API reference content that belongs in
docstrings. They SHOULD provide task-oriented or conceptual context that
AutoAPI cannot infer: installation paths, package selection, tutorials,
how-to guides, conceptual explanations, design tradeoffs that affect package
use, and links into generated API pages.

Sphinx documentation drift is a correctness issue. When changing public package
behavior, installation requirements, package layout, supported workflows,
middleware capabilities, generated schema behavior, notebook tutorial paths, or
documented examples, the Development Agent MUST update the affected Sphinx pages
in the same change or explicitly confirm that no published page describes the
changed behavior.

When adding a new public package capability, the Development Agent SHOULD decide
whether it needs one or more of the following documentation forms before the
task is complete:

- Tutorial: a learning-oriented walkthrough for a first successful use.
- How-to guide: a goal-oriented recipe for a specific task.
- Concept: explanatory material for design, semantics, or tradeoffs.
- Reference: generated API content from docstrings, plus minimal curated index
  pages.

Tutorials and how-to guides MUST prefer tested or manually verified examples.
If an example cannot be executed as part of normal validation, the page SHOULD
say what environment, optional dependency, or external service is required.
Sphinx pages that derive from notebooks SHOULD link to the notebook source
rather than copying large notebook bodies into prose pages.

Sphinx edits MUST be validated with `make docs` when they change Sphinx source,
toctrees, MyST syntax, cross references, generated API configuration, or
examples rendered by the published site. Markdown-only Sphinx edits MUST also
pass `make check`.

## Development Agent Commands

Before first validation in a session, the Development Agent MUST check that
`uv` and `pre-commit` are available in the active environment. If they are not,
the Development Agent SHOULD run validation commands through
`conda run --live-stream -n rdflib-reasoning make`.

After making significant Python changes, the Development Agent MUST run
`make validate test` and correct any errors.
After making changes to Markdown documents, the Development Agent MUST run
`make check` and correct any markdownlint errors.

- `make` commands may require usage of a conda environment (i.e., `conda run -n rdflib-reasoning make`)
- Use `make test` to run unit tests (should automatically use the virtual environment of `.venv`)
- `make test` outputs coverage details to the console produces artifacts: `.coverage`, `coverage.xml`, `htmlcov/`
- Use `make install-all` when a `.venv` environment does not exist or when dependencies change
- Use `make check` to lint everything **except** type checking
- Use `make validate` to lint everything **including** type checking

Normative guidance for **static typing of unit tests** (pytest return types,
local annotations, and Mypy vs Pyright suppressions) is duplicated under
**Testing expectations** in `rdflib-reasoning-axioms/AGENTS.md`,
`rdflib-reasoning-engine/AGENTS.md`, and `rdflib-reasoning-middleware/AGENTS.md`.
When that policy changes, the Development Agent SHOULD update all three copies
in the same change to avoid drift.

## Development Agent use of architecture and roadmap

- The Development Agent SHOULD consult `docs/dev/roadmap.md` before starting substantial feature work, release planning work, or any task where implementation priority or intended scope is unclear.
- The Development Agent MUST treat `docs/dev/architecture.md` as the authoritative intended design and `docs/dev/roadmap.md` as the authoritative release- and priority-oriented scope plan.
- The Development Agent MUST stop and verify that `docs/dev/roadmap.md` remains accurate before concluding substantial Python, middleware, or architecture-affecting work.
- The Development Agent MUST consider reprioritizing tasks and/or changing the intended scope of a release when implementation reveals an under-specified feature, a hidden dependency, a validation failure that changes delivery risk, or a mismatch between `docs/dev/roadmap.md` and `docs/dev/architecture.md`.
